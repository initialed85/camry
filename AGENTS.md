# Camry development workflow

## Workflow with PLAN.md

For non-trivial tasks, create a `PLAN.md` file in the project root:

- Document the context, checklist, and technical notes
- Use it as your work tracker - check off items as you complete them
- Add it to `.gitignore` - these are transient work-in-progress documents
- Delete or mark complete when ready to commit code changes

This keeps your working process visible without polluting version history.

## What is generated

Camry has three layers that are easy to confuse:

- `pkg/api/` is generated Go server/model code. Djangolang introspects the local PostgreSQL schema and writes it.
- `schema/openapi.json` is generated by the API binary.
- `object_detector/api/` and `pkg/api_client/` are generated OpenAPI clients for Python and Go.
- `frontend/src/api/api.d.ts` is generated by `openapi-typescript`.

The generated Camry code calls generic runtime/query code from the `github.com/initialed85/djangolang` Go module. A djangolang runtime fix normally needs a Go dependency update and API rebuild, not schema regeneration. A djangolang template/code-generation fix needs the full workflow below.

## Video status lifecycle

`video.status` is a free-text column (no enum) driven by whoever writes it. The states, in pipeline order:

- **`recording`** — inserted by the segment producer (`pkg/segment_producer/recording.go`) when ffmpeg opens a new segment (high-res and low-res producers each write their own row); `file_size`/`duration` are updated while live. The UI treats `status !== "recording"` as playable.
- **`needs detection`** — set by the segment producer on `onSave` (segment closed, `ended_at`/`duration`/thumbnail written). The recording half of the pipeline is done; the row is queued for the object detector.
- **`failed`** — set by the segment producer when a segment is abandoned/corrupt (file reopened before save, or cleanup on a row that never reached `needs detection`). UI shows an error icon.
- **`detecting`** — the object detector claims one unclaimed low-res row via `POST /api/object-detector-claim-video` (filtered on `status__in="needs detection,detecting"`, `is_low_res__eq=true`, ordered oldest-first), then patches `status="detecting"` on **both** the low-res row and its high-res sibling (matched by file name minus `_low_res`). The claim endpoint itself appends `(object_detector_claimed_until IS NULL OR object_detector_claimed_until < now())` to whatever filters the caller sends, so claiming `detecting` recovers work abandoned mid-inference once the lease (`CLAIM_LEASE_SECONDS`, dev 1200) expires — no row is handed out twice while its lease is live.
- **`needs tracking`** — the terminal state the pipeline actually reaches. After inference, the detector posts its tracks, posts detections (each stamped with the track row it belongs to), and patches both rows with `status="needs tracking"`, `detection_summary`, `track_summary`, and `object_tracker_claimed_until=now`.

**`needs tracking` is NOT handled by anything running in production.** It is effectively "processed/finalized", not "broken/waiting":

- No object-tracker workload is deployed (the cluster runs api, frontend, mediamtx, object-detector, postgres, redis, segment-producer, stream-producer).
- The claim endpoint exists (`POST /api/object-tracker-claim-video` / `POST /api/videos/{id}/object-tracker-claim`, gated on `object_tracker_claimed_until < now()`, ordered by `object_tracker_claimed_until ASC`) and `object_detector_v2` (Rust, not deployed) would write this status, but nothing claims `needs tracking` rows today.
- The detector only claims **low-res** rows, and the mid-run `status="detecting"` patch is written to the low-res row plus its high-res sibling only at completion. If a worker dies mid-inference, the low-res row stays `detecting` and its high-res sibling stays `needs detection`; since the detector never claims high-res rows, an orphaned high-res row is repaired by the hourly `video-fix` job, which mirrors finished low-res work (status, `detection_summary`, `track_summary`, `object_tracker_claimed_until`) onto the sibling. Its detections still display meanwhile, because the frontend resolves the low-res sibling at render time.
- The SQL view `video_with_seen_person` (migration `00003`) is the intended consumer: it selects `status = 'needs tracking'` person detections (score ≥ 0.55, >20 frames, last day) to derive "new person events" per camera. The view and its indexes are generated into `pkg/api/0_meta.go`, but the API exposes no `/api/video-with-seen-person` route, and no Go/Python/frontend code reads it.
- Detection queries in the frontend index by the **low-res** video id (`video_id__eq`), so a `needs tracking` low-res row is what backs the overlay boxes; high-res rows carry the mirrored status/summary for the list UI.

So when you check "how is Camry going": `needs tracking` rows sitting around forever is expected terminal state, not backlog. `recording` should be only the live segments (one high-res + one low-res per camera). A persistent set of `detecting` low-res rows alongside a roughly-equal pile of `needs detection` high-res rows means workers were killed mid-inference (pod restarts/node reboots) rather than a throughput problem — check `kubectl get pods -l app=object-detector` start times against those rows' `started_at`. Expired-lease rows come back to the detector on its own claim (no more than `CLAIM_LEASE_SECONDS` after the death) and the hourly `video-fix` job mirrors the finished work onto high-res siblings, so a *persistent* pile means the workers are not claiming at all. `./tmp/detector_queue.sh` reports claimable / leased / stuck / high-res pile, head-of-line lag, and arrival vs service per hour.

Two CronJobs in namespace `camry` run off the same configmap `prune`:

- **`prune`** (daily) deletes `/srv/media` files and `detection`/`video` rows older than 7 days, VACUUMs/ANALYZEs, then applies `fix.sql`.
- **`video-fix`** (hourly, `15 * * * *`) applies `fix.sql` and drops leaked publications. No media deletes, no VACUUM.

`fix.sql` is lease-aware: it re-queues only `detecting`/`failed` rows whose `object_detector_claimed_until` has already expired (live work is never pulled out from under a worker), deletes that video's `detection`/`track` rows before requeuing so a re-run cannot post a second set, and mirrors finished low-res work onto stranded high-res siblings. It never touches `needs tracking` on the low-res side. Because it re-queues expired-lease rows, a backlog of `detecting` low-res rows that keeps cycling back to `needs detection` means the detector workers are not claiming (crashes land in inference, not mid-write — the stuck rows have 0 detections). Run `./tmp/detector_queue.sh` for the numbers.

Leaked publications: djangolang names its publication and replication slot `djangolang_<DJANGOLANG_NODE_NAME>` with dashes folded to underscores (`raw_stream/stream.go`), so pod `api-0` owns `djangolang_api_0`. The slot is `Temporary: true` and vanishes with the connection; the publication is not temporary, so a pod killed hard (eviction, node reboot, SIGKILL) leaves its publication behind. Under the StatefulSet the next pod under the same ordinal re-adopts the name, so leaks self-heal; `video-fix` drops any `djangolang_*` publication whose name is not a live api pod. Check with `./tmp/pubs_script_test.sh` (stubbed kubectl/psql) and `./tmp/api_replicas_check.sh`.

## Object detector: knobs, tracking, fixtures

The detector (`object_detector/object_detector.py`) does one pass per claimed low-res segment: infer every frame, track objects across frames, then write. Knobs, all defaulting to today's behaviour:

- `MODEL_PATH` (image default `/srv/yolo26n.onnx`; `yolo26n.pt` is the PyTorch fallback), `IMGSZ` (`640`, or native `384x640`), `CONF` (`0.25`), `DEVICE` (`cpu|cuda|mps`), `HALF` (`0|1`), `BATCH` (frames per `predict` call, `1`).
- Claim lease: `CLAIM_LEASE_SECONDS` (default 60). The claim is a lease — while it holds, no other worker can take the row — so it must outlast one segment of processing. CPU segments take ~2 min, dev runs 1200. The segment producer uses the same idea with a refresh (`claimRefreshDuration = duration + 2s`).
- Tracking gates: `TRACKABLE_CLASSES` (person, car, dog, cat, motorcycle, truck, bus, bicycle), `TRACK_MIN_HITS` (4), `TRACK_MAX_AGE` (10 frames), `TRACK_MATCH_SCORE` (0.45), `TRACK_CONTINUITY_SECONDS` (120), `TRACK_STATIC_DISPLACEMENT` (0.06), `TRACK_SEED_LIMIT` (200).
- Fixture mode: `FIXTURE_DIR` (segment videos + `video-*.json` rows), `FIXTURE_OUT_DIR`, `FIXTURE_SOURCE_PATH` (prefix rewriting `/srv/media` paths), `ONE_SHOT_FILE_NAME`. No claim, no API, JSON output.

Tracking lives inside the detector: the model is cached per process, results are streamed frame-by-frame, and boxes are matched with IoU + centroid displacement. Identity is a UUIDv5 over (camera, class, first sighting ms) → `track.key`. Raw detections are never dropped; noise is rejected at the track level (`frame_count >= TRACK_MIN_HITS`). Identities continue across segments by seeding from `GET /api/tracks?camera_id__eq=...` with the time window applied **locally** — never as a generated datetime filter, because the generated client serialises offsets as `+0800` and the API parser rejects that.

Write order per segment (a crash mid-write leaves rows that `prune` re-queues):

1. `POST /api/tracks` in bulk with `key` = the tracker identity and **no `id`** (the API generates `track.id` and ignores a client-supplied one), then `GET /api/tracks?video_id__eq=...` to read the generated row ids back.
2. `POST /api/detections` in bulk, each row stamped with its API track row id (`detection.track_id` → `track.id`).
3. `PATCH` both video rows with the full model: `status`, `detection_summary`, `track_summary`.

`track.key` is the stable identity the UI labels with; `track.id` is the FK target. API `PATCH` zeroes NOT NULL columns the body omits, so every patch sends the whole model.

Fixtures live in `fixtures/<camera>_<timestamp>/` (segment `.mp4` + `video-*.json` + the live `video-*.detections.json`), fetched by `object_detector/tools/fetch_fixture.py`. Measure with:

```sh
CONF=0.33 IMGSZ=384x640 DEVICE=cpu \
  object_detector/.venv/bin/python object_detector/bench.py \
  --fixture fixtures/Side_Gate_2026-10-14T21_43 --label baseline
```

`bench.py` appends `{label, ms_per_frame, peak_rss_mb, frames, detections}` to `fixtures/<name>/bench.jsonl`; a zero-frame run is a broken run, not a result.

Runtime numbers (side-gate fixture, 384×640, conf 0.33, CPU): PyTorch `yolo26n.pt` 23.7 ms/frame, ONNX Runtime 16.2 ms/frame, **identical 327 detections**. The detector image exports the ONNX graph at build time (`docker/object-detector/Dockerfile`), which is why `MODEL_PATH` defaults to `.onnx`. The ONNX CPU runtime sizes its thread pool to the machine's physical cores and `OMP_NUM_THREADS` does not cap it, so the StatefulSet carries CPU `requests`/`limits` — without them two pods eat a 12-core node.

Claims (`POST /api/object-detector-claim-video`) are serialized by a transaction-scoped `pg_advisory_xact_lock` retried up to `timeout_seconds`, so a claim lock never outlives its connection: deleting pods cannot clear a "stuck" claim lock. Nothing claims `object_tracker_claimed_until` (the detector stamps it with `now` at completion), so the tracker claim endpoints stay inert.

## Local frontend browser validation

Use this workflow for frontend changes that need a real browser, especially video/media UI:

```sh
cd frontend
REMOTE=1 npm start
```

The Create React App dev server is at `http://localhost:3000`. `frontend/src/setupProxy.js` sends `/api` and `/media` to `https://camry.dev.initialed85.cc` when `REMOTE=1`; this is Camry's **dev** backend, not production. Keep the dev server running during browser tests and stop it with Ctrl-C when done. Confirm the app compiles and inspect API/media requests in the browser/network or dev-server logs.

### Headless Chromium against deployed dev

`tmp/browser_check.mjs` (gitignored) drives the deployed dev frontend with Playwright + the locally installed Google Chrome: `npm install playwright --prefix /tmp/pw`, then `CAMRY_TOKEN=$(kubectl --context home-dev -n camry get secret secret -o jsonpath='{.data.TOKEN}' | base64 -d) node tmp/browser_check.mjs`. It authenticates through `localStorage` (`camry-token`), scrolls the infinite video table to a target row (`tr:has(img[alt*="23:36:01"]):has-text("Side Gate")` — the row's `started_at` is one second off the segment filename), opens the modal, plays, and samples overlay-canvas pixels per mode. Notes: the modal's own toggle buttons do not exist (the modal inherits the app-level mode, and the header buttons are `aria-hidden` while the dialog is open, so toggle before opening); the table's thumbnails are keyed by `started_at`, not the file name; and video.js fluid sizing left the `<video>` element at 1×1 px in headless, so the script forces a player box with CSS before asserting overlay pixels.

### Playwright on CachyOS

Use the available Playwright MCP browser tools when they start successfully. This machine's MCP browser is configured for WebKit/iPhone emulation, but Playwright's Linux dependency installer assumes Ubuntu and runs `apt-get`; on CachyOS/Arch, `npx playwright install-deps webkit` fails because `apt-get` is unavailable. Don't treat that as an application failure or blindly run Ubuntu package commands. WebKit/iOS validation remains unavailable unless its dependencies are installed using an Arch-compatible method.

For a working Chromium fallback, install the Playwright browser if needed and use the Playwright package from the MCP npm cache with the installed Chrome executable:

```sh
npx playwright install chromium
PLAYWRIGHT_PACKAGE="$(find "$HOME/.npm/_npx" -path '*/node_modules/playwright/package.json' -print -quit)"
CHROME_BIN="$(command -v google-chrome-stable)"
PLAYWRIGHT_PACKAGE="$PLAYWRIGHT_PACKAGE" CHROME_BIN="$CHROME_BIN" node <<'NODE'
const path = require("node:path");
const { chromium } = require(path.dirname(process.env.PLAYWRIGHT_PACKAGE));
(async () => {
  const browser = await chromium.launch({
    headless: true,
    executablePath: process.env.CHROME_BIN,
    args: ["--no-sandbox"],
  });
  const page = await browser.newPage({ viewport: { width: 390, height: 844 }, isMobile: true, hasTouch: true });
  await page.goto("http://localhost:3000");
  // Use Playwright locators/evaluate to open a video and assert the controls.
  await browser.close();

NODE
```

For desktop, use a normal viewport. For touch-layout smoke testing, use a narrow viewport (e.g. 390x844) with `isMobile` and `hasTouch`; this is Chromium mobile emulation, **not** iOS Safari. When validating a player, inspect the rendered `.vjs-control-bar` and actually click a playback control after the initial render / inactivity interval; a visible-looking bar that is behind the video or has `pointer-events: none` is not usable.

If the dev backend or media is unreachable, record the failed requests and do not report a live-backend pass. You can still validate the frontend/player with Playwright route interception and a local generated media fixture, but label it as a mocked UI test, not a backend/integration test. For this situation, check connectivity to `https://camry.dev.initialed85.cc` directly as well as the dev-server `/api` proxy; a proxy 504 can be the upstream being unavailable. The media route should be mocked too if the remote media cannot be fetched.

## Local generation environment

For tmux/non-interactive workflows, start Compose detached and stop it explicitly:

```sh
./run-env.sh up -d
```

`run-env.sh` pulls/builds dependencies, starts Postgres/Redis/NATS, configures Postgres logical WAL, and restarts Postgres. `build.sh` waits for `post-migrate` to finish successfully and then connects to Postgres/Redis on localhost.

Check readiness with:

```sh
docker compose ps -a
```

Expected: `postgres` healthy, `redis` and `nats` up, and `post-migrate` exited with status 0. Follow logs with `./run-env.sh logs`.

Stop the stack while preserving the local Postgres volume with:

```sh
./run-env.sh down
```

To intentionally reset local databases/volumes, use `./run-env.sh down --volumes`. The legacy `./run-env.sh` (no subcommand) still follows logs in the foreground and tears down containers and volumes on exit.

## Selecting djangolang

Do not blindly use `FORCE_UPDATE_DJANGOLANG=1` when a release has just been tagged: Go's module proxy may not yet list the new tag, and `@latest` can temporarily resolve to an older release.

Pin the intended release explicitly first. For example:

```sh
GOPRIVATE=github.com/initialed85/djangolang \
  go install github.com/initialed85/djangolang@v0.1.37
GOPRIVATE=github.com/initialed85/djangolang \
  go get github.com/initialed85/djangolang@v0.1.37
```

Confirm `go.mod` before generating:

```sh
grep djangolang go.mod
djangolang 2>&1 | head
```

`FORCE_UPDATE_DJANGOLANG=1 ./build.sh` is useful when `@latest` is known to be correct, but it runs `go install ...@latest` and `go get -u ...@latest`; inspect the resulting `go.mod` and restore/pin it if the proxy selected an older version.

## Full generation workflow

With Compose healthy and the desired djangolang executable/module selected:

```sh
./build.sh
```

The script:

1. Introspects PostgreSQL and regenerates `pkg/api/`.
2. Builds the local generated API binary.
3. Generates `schema/openapi.json` using the running API.
4. Generates the TypeScript client and formats `frontend/src`.
5. Regenerates the Python client under `object_detector/api/`.
6. Regenerates the Go client under `pkg/api_client/`.

The script deletes and recreates generated client directories. If it fails after deletion, install the missing tool (most commonly `openapi-generator-cli`) and rerun; do not manually reconstruct generated files.

Useful flags:

- `SKIP_UPDATE_FRONTEND=1` skips `npm ci`, but still regenerates/typescripts and formats frontend source.
- `SKIP_DOCKER_COMPOSE_CHECK=1` skips only the readiness loop; it does **not** make PostgreSQL introspection unnecessary.

After generation, check that codegen fixes are present and compile:

```sh
# field-update generators should cover all fields using canonical Format* helpers
grep -n 'UpdateField\|UpdateFields' pkg/api/{camera,detection,video}.go

go test ./... -run '^$'
python3 -m compileall -q object_detector
object_detector/.venv/bin/pyright --pythonpath object_detector/.venv/bin/python object_detector/object_detector.py
git diff --check
```

## Runtime/deployment builds

`build-tag-and-push.sh` builds and pushes all images. The object-detector CUDA/PyTorch image is very large and can take a long time to build/push. If only generated/API code changed, a targeted API build is usually sufficient:

```sh
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -o ./tmp/api -trimpath ./cmd/api

docker build --platform=linux/amd64 \
  -t initialed85/camry-api:latest -f ./docker/api/Dockerfile .
docker image push initialed85/camry-api:latest
```

For frontend-only changes, avoid `build-tag-and-push.sh`: it also builds/pushes every other workload, including the large object-detector image. Build and push just the frontend image:

```sh
docker build --progress=plain --platform=linux/amd64 \
  -t initialed85/camry-frontend:latest -f ./docker/frontend/Dockerfile .
docker image push initialed85/camry-frontend:latest
docker buildx imagetools inspect docker.io/initialed85/camry-frontend:latest
```

The deployment uses mutable `:latest` with `imagePullPolicy: Always`; confirm the published digest and `linux/amd64` manifest before restarting anything. For a complete release, use the project script as requested.

## Kubernetes rollout checks

Before Kubernetes writes, check the current context and inspect the exact target workload/image. Use the intended context explicitly (normally `home-dev` or `home-prod-next` here). Only restart workloads whose image/code changed.

`home-dev` reconciles from `origin/master` of `~/Projects/Home/home-ops`, so live `kubectl` edits to Camry manifests, configmaps, replica counts, or the NVIDIA device-plugin config are reverted within about a minute. Commit and push the manifest, then restart what reads it; commit and push are pre-authorised for this kind of cluster config.

The `camry` `config` ConfigMap is regenerated by the API pod: keys added to it, or to the API's own environment, never reach the other workloads, and the detector's `env:` entries are rewritten. The detector's inference knobs (`DEVICE`, `MODEL_PATH`, `IMGSZ`, `CONF`, `CLAIM_LEASE_SECONDS`) are defaults in `object_detector/object_detector.py` with environment variables as overrides.

`august-desktop` advertises `nvidia.com/gpu` as time-sliced replicas (10 in `clusters/dev/cluster/device-plugins/nvidia-device-plugin.yaml`). A replica is a scheduling token, not a partition: every slice is a handle on the whole GPU, sharing VRAM and SM time. Changing the count needs a daemonset restart to re-register.

For the Camry frontend in `home-dev`, the verified workload is `deployment/frontend` in namespace `camry`. After pushing and verifying the frontend image digest:

```sh
kubectl config current-context
kubectl --context home-dev -n camry get deployment frontend -o wide
kubectl --context home-dev -n camry rollout restart deployment/frontend
kubectl --context home-dev -n camry rollout status deployment/frontend --timeout=300s
kubectl --context home-dev -n camry get pods -l app=frontend -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.imageID}{"\tready="}{.ready}{"\n"}{end}{end}'
kubectl --context home-dev -n camry logs deployment/frontend --since=5m --tail=60
```

Compare the ready pod's `imageID` to the just-published registry digest/platform manifest. Smoke-test the actual Nginx response through the service without depending on public DNS:

```sh
kubectl --context home-dev -n camry port-forward service/frontend 18080:80
# In another shell:
curl -fsSI http://127.0.0.1:18080/
# Stop port-forward with Ctrl-C.
```

For other components, inspect their actual StatefulSet/Deployment before using the equivalent restart. The API runs as a **StatefulSet with 3 replicas** (`podManagementPolicy: Parallel`, `updateStrategy.rollingUpdate.maxUnavailable: 1` — StatefulSets have no maxSurge), and each replica needs its own `DJANGOLANG_NODE_NAME` (from the pod name) because it owns a Postgres replication slot named `djangolang_<DJANGOLANG_NODE_NAME>` and a slot has exactly one active consumer. Stable ordinals (`api-0/1/2`) are the point: the slot and publication names are reused by the next pod under the same ordinal, so a hard-killed pod's leftover publication is re-adopted instead of orphaned. The API example is:

```sh
kubectl --context home-dev -n camry rollout restart statefulset/api
kubectl --context home-dev -n camry rollout status statefulset/api --timeout=300s
```

After an API rollout, check slots/publications and write latency with `./tmp/api_replicas_check.sh`: one active slot and one walsender per pod, and one `djangolang_api_*` publication per live pod (publications are not temporary, so a hard-killed pod leaves one behind until that ordinal comes back or `video-fix` drops it).

Then verify:

```sh
kubectl -n camry get pods -o wide
kubectl -n camry get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.imageID}{"\n"}{end}{end}'
kubectl -n camry logs -l app=object-detector --since=5m --prefix=true
```

For detector-only fixes, use the fast image flow when the detector base image already exists locally and the Dockerfile uses the frozen base: build and push only the detector image, then restart only its StatefulSet. Verify the new digest on every pod and check recent logs for model/API errors. For generated API changes, build/push the API image and restart only the API StatefulSet.

The detector matches high-res video rows to low-res detections using camera ID and nearby `started_at` time because the two segment writers may differ by a second in their filenames. Avoid sending Python-generated offset datetimes as API filters unless formatted as strict RFC3339 (`+08:00`); the generated client can serialize offsets as `+0800`, which the current API parser rejects.

Do not modify router/network configuration as part of Camry image rollouts.
